Why every page of your WordPress site is slow

A site that is slow everywhere is a different problem from a site with one slow page. Four measurements separate the usual causes: time to first byte, HTML size, image weight, and query count. Rowan Edge Cache records the last three for you and caches the first out of existence once pages are warm.

Measurement 4 — the database

Revisions, expired transients, orphaned metadata and spam comments all sit in the same tables every page reads. On a five-year-old site that is commonly 30–60% of the database, and cleaning it shortens every query that touches those tables.

Measurement 1 — time to first byte

Above roughly 600 ms on a cached page, the server is the problem: no object cache, an overloaded host, or PHP doing work per request that should be done once. A page cache turns this into a file read, which is the single largest win available on shared hosting.

Measurement 2 and 3 — HTML and images

An uncached WordPress page is often 60–120 KB of HTML, most of it whitespace, inline styles and plugin markup. Minification and lazy loading cut the bytes the browser must parse before it can paint. Images are usually the larger number: a 4000-pixel hero scaled to 1200 is four times the bytes for no visible gain, and converting to WebP or AVIF removes another 25–50%.

The honest test is a stopwatch, not a score. Load the same page five times with the plugin disabled and five times with it enabled, on the same network, and compare the median. Then check the cache page for a miss count that keeps rising on pages you never visit - that is usually a query string, a cookie, or a form that should have been excluded.

Rowan Edge Cache records what it did per request: whether it served from cache, how many bytes it saved, and how long generation took. Those three values are enough to tell a working setup from one that only looks configured.

Who this is for

The useful test: do you administer the site yourself, and does it run on hosting you can restart? If yes, Rowan Edge Cache is the whole performance stack. If someone else owns the platform and the CDN, the plugin is a smaller piece of a larger puzzle and the counters here will tell you how much of the problem was yours to begin with.

What it does not do

It will not make a slow host fast, and it will not score well on a lab test that disables caching. It does not touch other plugins' tables, does not replace Redis, and does not promise a Core Web Vitals pass on a theme that ships six JavaScript libraries. Every claim on this page is something the plugin itself performs.

Frequently asked

The dashboard shows a high hit rate but the site feels slow — why?

A hit rate only covers pages that were cached. Check whether the slow page is excluded, whether it is a logged-in view, and whether images on it are the problem.

Does caching help admin pages?

No. Logged-in requests bypass the cache by design; admin slowness is usually queries or host CPU.

How long should a cached page take?

On a modest server, 50–200 ms of server time. If it is much more, the cache is missing the request.
